# CHANGELOG
## AI Customer Support Platform — significant project changes

## 2026-10-30
### P3b — cases reply + handoff + `Idempotency-Key` + message history
- **`POST /v1/cases/{id}/reply`** — an outbound `messages` row on the case's conversation, gated `cases.reply`. Refused (`409 conflict`) on resolved/closed cases (reopen first) and on cases without a conversation. **The human half of the AI vs human send-lock is now real**: the case row is locked `FOR UPDATE`, so concurrent human sends serialize; the AI side lands with ai-orchestration and races nothing. `delivery_state` starts `pending` honestly — no channel adapter exists yet, so nothing is claimed "sent"; the channels slice owns `pending → sent → delivered`
- **`Idempotency-Key` honoured on reply** — and it shipped with **zero new migrations**: migration 003 already carried `messages.idempotency_key` with its `(tenant_id, idempotency_key)` unique index, so the storage the P3-1 tracker row called for was pre-built. A retry with the same key returns the ORIGINAL message (`idempotent_replayed: true`) with no duplicate row, audit entry or outbox event; a key already bound to a *different conversation* of the tenant is a `409 conflict` (a retry must never "succeed" against the wrong thread). New error code `conflict` (409) in the catalog
- **`POST /v1/cases/{id}/handoff`** — inserts a `handoffs` row in state `requested`, writes the `handoff.requested` case_event (which preserves the optional free-text summary as timeline metadata), the `handoff.requested` **outbox event** (first consumer-facing producer beyond the lifecycle pair) and the audit row — all in one transaction. Destination eligibility enforced: queue must exist in-tenant (foreign/unknown queue → `404`), and when both channels are known it must match the case's channel (`409`). **One active handoff per case**: a repeat request returns the same row with `created: false` (idempotent by behaviour, like resolve); once it leaves `requested`, a new request creates a new row. Permission stays `cases.reply` (escalation is agent work; if a handoff mutates assignment/queues it moves to `cases.manage`). The ACCEPT endpoint lands with the routing slice
- **Message history in the detail response** — `GET /v1/cases/{id}` now returns `messages` (newest first) paged by `?message_limit=` + `?messages_cursor=`, an **independent keyset cursor** from the timeline's `?limit=`/`?cursor=` because the two page different tables (`messages` by `(created_at, id)`, `case_events` by `(occurred_at, id)`) with the same microsecond-exact `to_char` wire format. A case without a conversation returns `messages: []`
- **Outbox: `message.sent` added as an additive catalog entry** (API_CONTRACTS §3) — agent replies need a producer for the widget live stream; Architecture §9's list doesn't name it, and the compatibility rule (consumers tolerate additive events) covers the registration. Audit vocabulary: `message.sent`, `case.handoff.requested` — metadata carries ids/states/reason, never a reply body or the handoff summary
- **Body storage compromise, recorded**: the reply body is stored whole in migration 003's `body_preview` column (validated ≤ 10 000 chars) because `body_ref` points at object storage that no channel adapter writes yet — reviewed when the channels/content slice lands
- **Tests 177 → 194** (api 158 → 175): 12 new integration tests over the real app — reply row + atomicity (audit without the body, exactly one outbox event), idempotent retry returning the original message, cross-thread key → 409, reply on resolved/bare cases → 409, cross-tenant reply 404 writing nothing, message-history keyset walk (3 rows, 2 pages, newest first), handoff row + timeline + outbox + audit with the summary never in audit, active-dedup + decline-then-new handoff, destination eligibility (unknown/foreign 404, channel mismatch 409), and the viewer/write boundary extended to reply — plus 5 controller unit tests (reply body cap, Idempotency-Key charset/length, handoff body, response mappers). **One real bug caught by the tests before commit**: `RETURNING <m.-prefixed columns>` inside the INSERT (no alias exists there) 500'd the whole reply path — the column list is now prefix-parameterized
- Verified: boot smoke on the built server (`/health` 200, default-deny `/v1/cases` 401, both new routes mapped), **lint 0, typecheck 4/4, build 3/3, vitest 194/194 (api 175 + worker 12 + shared 7), 6/6 turbo tasks**, secrets audit clean
- **Deliberately out**: `case.created` producer (no case-creation endpoint yet), `AI-handled` list filter (no column yet), handoff accept/decline endpoints (routing slice), `body_ref` object-storage writes (channels slice)
